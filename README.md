# SQUARE (Pulse (pLsE), 1998) - reverse engineering + JavaScript port (work in progress)

"square" by Pulse, final version of the SERVO98 compo entry (code Statix = Alex Evans, Dune; gfx Haplo, Zeb; music Mario, Shad). DOS, PMODE/W 1.22 + Watcom C + MIDAS 0.7.b1, mode 13h / unchained VGA, FPU heavy.
Originals (`SQUARE.EXE`, `SQUARE.PAK`, `*.LZW`, `SQUADEMO.XM`, NFO) are untouched next to the port and git-ignored.

## Status
Reverse engineering has started (see `re/NOTES.md`, the running log). Six scenes run from the original's own recompiled code (see the recompiler bullets); the others are hand ports or not done. What exists:
* the EXE unpacks and **runs under Unicorn** (`re/unpack_clean.py`, `re/emucore.py`): it opens the PAK, prints its startup text, goes through the MIDAS menu (No Sound) and reaches mode 13h with the first scene running.
* **SQUARE.PAK fully understood as a container and decoded** (`re/pak_dir.py` lists the 67 files, `re/pak_extract.py` decodes all of them by running the original loader; every size equals the directory's usize). The codec is reimplemented in `web/js/lzw.js` and verified against the guest on all 67 files + PEOPLE/ZEBOU.LZW (`node tools/cmp_lzw.mjs`: 69 streams, 0 differing).
* timing model found (60 Hz timer ISR + music position order*64+row), scene order of `main` identified (~15 scene functions).
* `re/harness.py`: 60 Hz callback + music-position hook + frame grab at the page flip, now with a post-start-up **snapshot** (`SNAP=`/`LOAD=`) and `JUMP=addr TOFF=sec` to run one scene directly. The earlier 'stuck dark scene' was a bug of mine (status struct hook); with it fixed the whole demo runs to the end under Unicorn and the scenes have start times (`re/NOTES.md` Session 4, `figures/scenes_contact_sheet.png`).
* **PEOPLE.LZW is decoded and its DCT layer is ported bit-exact**: `web/js/dct.js` reproduces all 117 frames (192x144 grey) of the original frame decoder (0x38f7b, run under Unicorn) with 0 differing bytes (`node tools/cmp_people.mjs DIR`, see `re/NOTES.md`). The .LZW files use the PAK bit-stream codec, now ported (`web/js/lzw.js`). ZEBOU.LZW decodes to a `mhwanh` 320x200 image stream, not understood yet. Neither is shown in the web player yet.
* `web/`: player (the XM through libopenmpt, 4:3 stage, pause + seek) that shows the last scene (people, from 3:38) from the original PEOPLE.LZW: frame blend and 2x upsample are bit-exact vs the original (`node tools/cmp_people_blend.mjs`), the radial zoom blur (`web/js/blur.js`, 120 golden calls bit-exact), the PULSE/SQUARE logo composite (logo.raw read from the original SQUARE.PAK in the browser through `web/js/pak.js`, 60 golden frames exact) and the palette fade-in (approximated) are ported too, see `figures/people_scene_player.png`. All other scenes: not ported.
* **Static recompiler (new, `re/x86js.py` from ../plastikx, extended)**: scenes 0x29a81 (the opening portrait, 632 flips, 320x480) and 0x338a5 (dune texture, 120 flips) are translated from the original machine code to JS (`web/js/sqr.gen.mjs`, 34 functions, 0 unhandled instructions) and run frame by frame by `web/js/rcscene.mjs` on a 43-51 KB entry snapshot plus the original PAK. Diff against the Unicorn run: **752 flips, 749 bit-exact**, the DAC palette writes identical (except the last interval of the portrait scene). Both scenes are in the player at their times (`figures/recompiled_portrait_scene.png`, `figures/recompiled_dune_scene.png`); about 8 ms (portrait) and 23 ms (dune) per flip in node after hand-written JS patches for the per-pixel loops, so inside the 33 ms flip budget. The 3 non-exact frames are not caused by `sin` (Unicorn uses libm double sin; checked) nor `exp` (unused there); cause still open, see NOTES Session 6. Method, natives, limits and sizes: `re/NOTES.md` Session 6; check with `node tools/rc_run.mjs` and `node tools/rc_scene_test.mjs`.
* **Four more scenes recompiled (Session 8, `re/NOTES.md`); one (0x1faa1) is in the player on the music clock; 0x366f2, 0x305f7 and 0x2edbd are NOT wired until exact (0x366f2 has a 38 KB asset `rc366.bin.gz` but is exact only for its first 80 flips) (0x305f7 and 0x2edbd are recompiled and run in node but are NOT wired: their snapshots need heap memory (0x305f7: ~1366 pages, 1.6 MB gz) that the range search did not isolate) (module now 97 functions, 0 unhandled): 0x1faa1 (73.43 s, 157 flips) is **bit-exact** (157/157, DAC exact, 25 ms/flip in node, asset 14 KB); 0x366f2 (21.07 s, metaballs, ~942 flips; asset 38 KB; 63 ms/flip in node, ~46 with a warm JIT) is exact for the first 80 flips, afterwards a feedback scene whose blob rims are off by one intensity step (860 of 941 frames differ, picture visibly the same); 0x305f7 (52.43 s, 630 flips) first differs at flip 42 (1-pixel shifts), then drifts (587 frames differ, ~51 ms/flip); 0x2edbd (78.67 s, 656 flips) differs by +-1..3 palette steps on ~14% of the pixels from flip 1 (~90 ms/flip, i.e. it will lag the music in the browser). These three are **approximations, not golden-exact**; ruled out as the cause: libm sin/cos, exp, double rounding of the 24-bit x87 ops, song-position sampling (NOTES Session 8). Where a scene runs slower than 33 ms/flip the picture lags behind the music (time-budgeted stepping), it never stalls the audio.

## Exact vs approximated (be honest)
Exact: PAK/LZW codec (lzw.js) and PAK directory (pak.js, all 67 entries equal the guest decode), PEOPLE frame decoder (dct.js, 117 frames), people blend + 2x upsample (people.js, 120 golden calls), radial zoom blur 0x2a8e8 + asm 0x58000 (blur.js, 120 calls) including its argument curves given p and S (the two sine-noise curves, with the x87 running at 24-bit precision), logo composite (60 frames). Approximated: the people frame position p and decay S (own 60 Hz tick model of the original's dt-based loop), the palette fade-in (about 1% of sampled DAC values off by one), and the noise table 0x110be4 (one captured run: the guest fills it with rand() whose seed I did not reproduce). Recompiled (original code run as JS, not understood-and-ported): scenes 0x29a81 and 0x338a5, bit-exact against the guest on 749 of 752 flips (3 frames have 4-78 stray pixels off by 1-3 levels, cause not found: suspects are the `Math.sin`/`Math.exp` natives, `exp` replaces the x87 f2xm1 sequence), x87 run at 24-bit precision (float32 rounding); malloc is a bump allocator, free a no-op; time model = 2 ticks of 60 Hz per flip (not the real machine's frame rate). Missing: all other scenes (only named/timed). Earlier verified facts are the container/codec behaviour of the PAK (decoded by the original code itself) and the entry point / selectors / timing sources listed in the notes.
